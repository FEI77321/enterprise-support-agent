# ADR-0001：当前继续使用 ChromaDB 作为主向量检索组件

- 状态：Accepted（秋招收缩版）
- 日期：2026-09-08
- 决策范围：Enterprise Support Agent 的默认主检索链路

## 背景

项目既有主链路使用本地 ChromaDB 进行向量检索 fallback，并已被固定 RAG 评测覆盖。RAG 2.0 新增了 SQLite 文档、版本和 Chunk 元数据，以及一个用于隔离验证的词面检索入口。

此时可选的扩张方向包括：

1. 立即将新 Chunk 双写到 ChromaDB；
2. 新增 Milvus 并实现数据迁移、双写、回滚与性能压测；
3. 保持现有 ChromaDB 主检索，SQLite 新链路仅承担文档治理和隔离验证。

## 决策

选择方案 3：**默认主链路继续使用 ChromaDB；SQLite 实验检索保持独立、默认关闭，不迁移 Milvus，也不进行 ChromaDB 双写。**

## 决策依据

| 维度 | 当前证据 | 影响 |
| --- | --- | --- |
| 已有稳定性 | 旧主链路固定集 Recall@3 `1.0000`、FPR `0`、MRR@3 `0.9551`、nDCG@3 `0.9602` | 没有“当前向量库造成真实业务问题”的证据。 |
| 新能力目标 | 本轮首先验证 hash 幂等、版本、失败隔离、Chunk 与来源回链 | 这些问题与更换向量库无直接因果关系。 |
| 数据规模 | 当前是本地项目和 synthetic / 小规模文档验证 | 不足以证明需要 Milvus 的分布式扩展能力。 |
| 迁移成本 | 双写、索引构建、数据一致性、回滚、监控、压测都需要额外设计与测试 | 会挤占秋招中算法、基础知识和面试演练时间。 |
| 可回退性 | ChromaDB 既有路径已存在；SQLite 实验路径有独立开关 | 先隔离验证可以最小化回归风险。 |

## 后果

### 正向后果

- 保留已有主 RAG 能力和评测基线；
- RAG 2.0 的收益可归因到摄入、版本和来源治理，而不会与向量库迁移混在一起；
- 代码范围小，能在秋招前形成可讲、可守、可回退的闭环；
- 不把“能部署 Milvus”误写成“解决了检索质量问题”。

### 接受的限制

- 新 SQLite 实验检索不是向量检索，也未与 ChromaDB 数据同步；
- 当前没有并发、千万级规模、分布式索引或生产 SLA 证据；
- 文档新增后不能自动进入既有 ChromaDB 主检索，这是当前明确保留的边界。

## 重新评估条件

同时或大部分满足以下条件时，才创建新的 ADR / POC 来评估 ChromaDB 扩展或 Milvus：

1. 有真实授权语料和稳定的检索评测集；
2. 已定义吞吐、并发、索引延迟、内存和持久化指标；
3. 现有 ChromaDB 在这些指标或功能上出现可复现瓶颈；
4. 有能力验证双写一致性、索引重建、回滚、监控和故障恢复；
5. 迁移不会挤占更高优先级的秋招准备。

在条件不具备前，本 ADR 的结论保持有效：**先证明数据治理与检索收益，再讨论分布式向量库。**
