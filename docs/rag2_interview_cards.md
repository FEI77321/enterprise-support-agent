# Enterprise Support Agent RAG 2.0：面试深挖题卡

> 使用方法：先用“30 秒答案”独立口述；面试官继续追问时再补充“可展开点”。所有数字和边界都可回链到项目代码与 `eval/` 脚本。

## 1. 原系统的真实缺口是什么？

**30 秒答案：**

原系统已有 Markdown、关键词和 ChromaDB 向量检索，但它把文档作为静态内容使用，缺少版本、内容幂等、解析失败隔离和精确来源回链。也就是说，文档更新、扫描件解析失败，或者需要回答“这条知识来自哪一版、哪一页”时，原链路没有一个可验证的治理闭环。因此我没有先换模型或向量库，而是先补文档进入知识库后的可追溯性。

**可展开点：**

- 同一制度的 v1 / v2 必须有一个 active 版本；
- 扫描 PDF 没有可靠文本时不能产生 Chunk；
- 回答要能回到文件、版本、标题和页码；
- 这些是检索质量之外的“证据可信度”问题。

## 2. 为什么先做 isolated synthetic 实验，而不是直接改线上主路径？

**30 秒答案：**

旧主链路已有固定黄金集和稳定指标，直接把解析、切块、版本、新检索策略一起接入，会导致指标变化无法归因，也可能破坏已有回答。于是我把新能力放在临时 SQLite 和固定 synthetic 语料中做契约验证，先单独证明每个环节正确，再用默认关闭的 feature flag 做最小接入。

**可展开点：**

- 主链路默认关闭时指标保持 Recall@3 `1.0000`、FPR `0`、MRR@3 `0.9551`、nDCG@3 `0.9602`；
- 这不是“线上 A/B 实验”，而是本地隔离实验；
- 每一步都可跑独立脚本，而不是只看一次聊天效果；
- feature flag 提供关闭和异常回退路径。

## 3. 新链路的核心设计是什么？

**30 秒答案：**

核心是“文档版本治理 + 可控检索准入 + 来源回链”。文件先计算 SHA-256，在同逻辑文档内判断是否重复；成功解析后按标题切为 Parent / Child Chunk；成功版本激活，旧版本标记为 superseded，失败扫描件无 Chunk；检索只看 active 文档的 indexed Child Chunk。命中结果再映射为兼容旧 API 的 Source，并补充版本、标题和页码。

**可展开点：**

```text
Path → hash → parse → chunk → SQLite Repository
     → active version → INDEXED 准入 → retrieval result → Source
```

- `INDEXED` 在本轮仅表示可以进入 SQLite 实验检索池，并非已向量化；
- Markdown 可返回标题路径，基础 PDF 不伪造视觉标题；
- 失败版本被持久化，便于审计，但不能污染答案依据。

## 4. 指标相比基线提升了什么？

**30 秒答案：**

在 synthetic 固定集的 document-aware lexical 实验中，Recall@3 从 `0.9375` 提升到 `1.0000`，MRR@3 从 `0.9062` 提升到 `0.9271`，nDCG@3 从 `0.9144` 提升到 `0.9457`，FPR 保持 `0`。这说明先聚合候选文档、再在文档内选 Chunk，能减少跨章节证据被全局排序遗漏的问题。

**可展开点：**

- 数字只适用于 synthetic 固定集；
- 不应说“线上指标提升”或“模型能力提升”；
- 当前主 Agent 默认仍走旧路径，实验策略没有替换生产默认检索。

## 5. 为什么指标变好仍然不立即接入主 Agent？

**30 秒答案：**

因为检索指标好只是接入条件之一，不是充分条件。实验数据规模小且是 synthetic，文档版本、失败隔离、来源回链和异常回退还需要先完成；同时主链路已有稳定评测。当前我选择默认关闭、旧关键词无结果后才尝试实验检索，命中才返回，异常仍回到原向量 fallback。这比一次性替换更容易观测和回滚。

**可展开点：**

- 把“策略有效”与“适合全量默认流量”分开；
- 先验证事实，再扩大影响面；
- 未把实验分支复制进 LangGraph，避免两套编排长期漂移。

## 6. 为什么不直接上 MinerU / OCR？

**30 秒答案：**

我先用两份表格 PDF 做了 5 次 pypdf 基线。两份文件的业务事实锚点都是 5/5、页码可用，平均解析约 4.673ms 和 3.661ms，但表格行列没有保留。MinerU 能补这个缺口，不过当前环境是 Windows + Python 3.13，官方 Windows 支持范围是 Python 3.10—3.12，而且完整接入需要独立环境、依赖和模型。没有真实表格单元格级问答需求前，先记录边界比强接更符合投入产出比。

**可展开点：**

- 扫描件当前是 `FAILED + 无 Chunk`，比空内容进入检索安全；
- 重新评估触发条件：真实授权复杂 PDF、明确表格问答、独立 Python 3.12 环境、可量化收益；
- 这是时间盒决策，不是宣称 MinerU 不好。

## 7. 为什么 RAG 2.0 不把新 Chunk 直接写进 ChromaDB？

**30 秒答案：**

这次目标首先是验证摄入、版本、失败隔离和来源回链，不是迁移向量库。直接双写 ChromaDB 会引入索引构建、一致性、回滚和评测归因问题；而旧主链路没有可复现的向量库瓶颈。因此新 Chunk 只在 SQLite 隔离检索中验证，默认主链路继续使用 ChromaDB。是否接入向量库，需要基于真实数据、吞吐和质量评测再决定。

## 8. 如何保证新功能不破坏旧功能？

**30 秒答案：**

我把隔离放在三个层面：数据使用临时 SQLite 数据库做契约验证；运行时由默认 false 的环境变量保护；调用位置只在旧关键词检索无结果后。开关关闭时函数不会被调用；开关开启后即使实验检索报错，也会记录 workflow step 并继续原有向量 fallback。最后用 API 契约和旧 RAG 固定集回归确认默认路径不变。

## 9. Parent / Child Chunk 为什么要同时存在？

**30 秒答案：**

Child Chunk 比较小，适合精确匹配和排序；Parent Chunk 保留更大的标题上下文，适合解释这段内容属于哪一章、必要时补全上下文。检索主要返回 Child Chunk，但结果带 `context_chunk_id`，因此后续可以扩展为“命中小段、展示大段”的引用策略，而不牺牲当前最小实现的可解释性。

## 10. 你会怎样进一步验证它是否值得正式接入？

**30 秒答案：**

我会先获取脱敏且授权的真实文档和问题集，明确检索正确性的标注口径；然后对旧路径、SQLite 实验路径和可能的向量化接入做并行离线评测，除了 Recall、MRR、nDCG，也增加来源正确率、版本正确率、失败文件误召回率、延迟和人工可读性。达到事先定义的阈值后，才灰度扩大 feature flag 范围，并保留一键关闭与回滚。

## 60 秒总述模板

> 我在已有企业 IT 支持 Agent 上补了一条受控的 RAG 2.0 文档摄入实验链路。原系统能检索静态 Markdown，但缺少文档版本、失败隔离和精确来源治理。我先用 SHA-256 做同逻辑文档幂等，成功文档解析后按标题切 Parent / Child Chunk，扫描件失败则不产出 Chunk；新成功版本激活，旧版本 superseded。检索只看 active 且 indexed 的 Child Chunk，结果能回到文件、版本、标题和页码。为了不影响已有主链路，我把它放在默认关闭的 feature flag 后，并且仅在旧关键词检索无结果时才尝试，异常就回到原有向量 fallback。整个过程用摄入 5/5、来源 3/3、检索 3/3、开关 2/2 等契约证明；复杂 PDF 也做了时间盒测试，确认基础 PDF 足以满足文本与页码，但表格结构和 OCR 暂不因技术堆砌而接入。这个项目的重点不是多加组件，而是在可回退条件下把 RAG 的证据链做可信。
